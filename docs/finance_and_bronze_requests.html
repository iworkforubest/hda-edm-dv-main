Finance — four questions about negative GL amounts

A data-quality rule drops any general-ledger line whose debit or credit is negative. Across 19,057,752 GL rows it catches exactly two journals, both from BRPLM, both FY2025, both balancing to zero. Whether they belong in the warehouse is an accounting judgement, which is why it is a question rather than a change. Nothing has been deleted; the rows are quarantined with the rule that caught them recorded alongside.

IdQuestionWhat it changes
GL-1 Is a negative debit or credit a legitimate posting in this ledger — for example a correction posted in place rather than by swapping sides? If yes, the rule excludes valid postings and two journals are missing from the warehouse. If no, they are correctly quarantined.
GL-2 If they are legitimate, should the rule be removed, or downgraded from drop to warn so they load and stay visible? Either is straightforward. drop keeps them out entirely; warn loads them and records the match.
GL-3 Should ordbtamt / orcrdamt be treated the same way as the functional amounts, whichever way GL-1 goes? Today they are inconsistent: 16 negative originating-currency values sit in the warehouse untouched. Either answer is fine; the mismatch is not.
GL-4 Are BRPLM 496073 and 496157 anything you recognise — a known correction, an import artefact, something already investigated? Two journals is few enough to look at individually, which is why we are asking rather than generalising.

Why it matters now. The quarantined rows block a control: the reconciliation gate refuses to attribute a quarantined row to a delivery it cannot identify, so five downstream checks do not run while these two journals sit there. We could suppress that and have deliberately not — the gate is right, and the honest fix is to settle whether the rows belong in the warehouse.

Bronze — one request blocking a control today

BRZ-12 Bronze Request sent · still open

Carry a control / ETL id in the Fieldglass payload — when Snaplogic pulls Fieldglass over the API and lands it into Bronze, include an etl_id / control_id style value as a field in the payload it writes. One value per run, the same on every record that run delivers, plus the number of records that run delivered.

CORRECTED 28 September. This supersedes the reduced form this page carried before. That earlier note said a stamp on the landed data was no longer asked for and that no column would be added. That reduction was wrong: it removed the part the control depends on. The gate groups landed rows by the id, so a manifest row on its own gives it nothing to group — every row still has to say which run brought it in. Its own message, quoted below, asks for a manifest_column, which is a column on the row.

Nothing else about the feed changes: not how Fieldglass is called, not what is landed, not when. One extra field in the payload, plus a count per run.

What it blocks, measured 27 September. The loop-1 reconciliation gate reported status=NOT_EVALUATED asserted=0 on the last full vault load. Its own message: “no ACTIVE reconcilable binding declares a manifest_column, so no row carries a manifest_id to group by and no producer can exist”. Without an id there is nothing to group by, so landed + (quarantined − superseded) = approved cannot be evaluated at all. The gate is honest about asserting nothing rather than passing silently — but it is asserting nothing.

For the three feeds that de-duplicate on load, a stamped id is necessary and not sufficient: loop-1 also needs a count taken after de-duplication, and that count is ours to compute, not yours to supply.

Bronze — one new request, not yet numbered

new Bronze Raised · sent 28 September

A workday / workday_raw schema pair in the bronze catalog, landing Workday reference values the same way every other source system lands.

Why. Logan's DCDDs specify the Workday load by reference: a field does not carry a name, it carries a Reference_ID whose value Workday already knows. In the customer-invoice DCDD, 27 of the 91 fields we populate validate against those references — 108 across the full workbook, including the rows marked Do Not Populate. Nothing in this estate holds them.

Measured 27 September. 01_usnc_bronze_dev has no schema matching workday or wd_. The catalog already follows a <source> / <source>_raw convention — fieldglass, ukg, hubspot — so this is that pattern applied to one more system, not a new shape.

Two interfaces, and they are not interchangeable. Snaplogic calling the SOAP Get_References service needs nothing new from Workday. Databricks Lakeflow Connect's Workday connector ingests Reports-as-a-Service instead, which would require somebody in Workday to publish a custom report first. The choice decides who else has to be asked.

Until this lands, the values land in an interim silver schema, workday_landing, which is built to be deleted: when Bronze exists the two entity bindings move and the schema is dropped.

Platform — the request that was refused, and what replaced it

PLT-2 Platform admin ANSWERED 28 September · refused, and replaced with a better design

WITHDRAWN. The ask was to add the load identity to global_dataplatform_pipeline_job_runners. The platform team declined, and they were right to.

CORRECTED 28 September. This page previously asked for that membership and called it “the group every mask function admits by name”. Both halves are now wrong, and the sentence is left here only so a reader who saw the earlier version can tell what changed.

Their argument, and it is the better one. That group is operational — its function is to let data engineers run jobs. The service principal did not need it to run anything; it needed it only because mask_money unmasked for that group. That makes it a data-access grant wearing an operational group’s clothes: anyone added merely to run jobs would also get cleartext currency.

What exists instead. A dedicated group, scope_unmask_currency_values, with the pipeline service principals already in it. People who need cleartext amounts are added by explicit request rather than as a side effect of being able to run a job.

Our side, and it is two functions rather than one. The reply named mask_money (27 declared columns). We are also repointing mask_money_double (4 columns, including nhl_general_journal_line.ordbtamt and orcrdamt — the originating-currency amounts assert_journal_integrity reads). Changing only the first would have half-fixed it. The three PII masks keep the operational group: a currency group is the wrong exemption for a personal name, and no column declares them today.

NOT YET DEPLOYED, and it must not go everywhere at once. Four targets — weu_tds, uks_tds, aue_tds and dev — declare no run_as, so their loads run as a named human who is in the operational group but not the currency one. Deploying there would have the money masks deny the loading identity, and a materialized view would then write those NULLs into the insert-only silver vault. That is the same irreversible harm this request was raised to prevent, arriving from the opposite direction. usnc_tds runs as the service principal and is unaffected.

What we have not done

We have not suppressed the reconciliation gate, deleted a quarantined row, or worked around the missing manifest id. We have not created a Workday schema in a catalog that is not ours. Each of those would turn a visible gap into an invisible one, and every item on this page is recoverable precisely because nothing was worked around.
