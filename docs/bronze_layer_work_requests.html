BRZ-14

_backfill tables infer their column types; the live tables do not

Losing data now Added 4 Sep
Ask
Land the same column types on the _backfill path as on the live path, and reload the tables already written. We are not asking for a conformance layer or a schema change — only that a column arrive as the same type in a tenant's backfill table as in its live table.
Why this is yours and why it is urgent
This is not a vault problem and fixing it does not depend on anything we do. It is happening inside Bronze, to Bronze's data, and every consumer of a _backfill table inherits it. We found it because a union across tenants would not type cleanly, but the loss is already written and it is not recoverable by casting after the fact — the digits are gone.
Evidence measured 4 Sep, 01_usnc_bronze_dev
The correlation is exact. Across all 58 io_distributed_jobposting tables — 30 live plus 28 _backfill, so 30 tenants, not 58 — 15 columns carry two different types. Counting every instance: DOUBLE appears 153 times and every one is in a _backfill table. Live tables are STRING in all 330 instances. Not one live table is typed DOUBLE.

It is estate-wide, not a job-posting quirk. Nine table families across fieldglass_raw and fieldglass_client_owned_raw have DOUBLE-typed columns, and in every family it is only the backfill tables: io_worker 33 columns, io_distributed 15, io_timesheet 15, io_jobposting 13, co_worker 12, co_timesheet 8, co_jobposting 5, co_distributed 5, io_jobseeker 4. io_worker being the worst is the least comfortable part — worker data is the personal-data domain.

Measured loss, one table. io_distributed_jobposting_cencora_backfill.zip_postal_code is DOUBLE with 12,491 non-null values, of which 556 are under five digits and 10 are under four. A US ZIP is five digits, so those have lost at least one leading zero. A DOUBLE cannot represent 00965; it can only hold 965.0. That is arithmetic, not a formatting preference, and no cast recovers it.

A date in a float. io_distributed_jobposting_albertsons_co_backfill.job_posting_closed_date is DOUBLE while the same column is STRING in the other 57 tables.

The likely mechanism, for what it is worth: schema inference on a column that was empty or all-numeric in the backfill file. It would explain close_comments and close_reason — free-text columns — arriving as DOUBLE in exactly one table each.
What it costs us, so you can weigh it
Less than it costs you. We can cast on read, and will. But it makes BRZ-4 unanswerable as posed: that item asks which row wins when a base and a _backfill table both hold one, and if the two tables disagree about a column's TYPE then neither “take the backfill” nor “take the live” is a complete answer — a cast has to be specified either way, by someone. One fix here removes that question.
Done when
A column has the same type in a tenant's backfill table as in its live table, and the tables already written with an inferred type are reloaded.
BRZ-1

Enable Change Data Feed on _raw tables

Blocks all loads
Ask
Set delta.enableChangeDataFeed = true on _raw tables as part of the Auto CDC migration, not after it.
Why
Once _raw becomes an APPLY CHANGES INTO target it stops being append-only, so the vault loses its only streamable tier and the operation flag is consumed rather than emitted. Without a change stream the vault cannot tell a new row from a re-delivered one — every satellite re-appends every row on every run, and no existing gate objects.
Evidence
No _raw table carries a CDC operation column today. Columns are Auto Loader landing metadata only.
Done when
_change_type is readable from _raw via readChangeFeed.
Cost
A table property. Cheap while the migration is being built, awkward to retrofit afterwards.

BRZ-15

The Fieldglass job-posting feed has no clock

Added 5 Sep
Ask
Add a modification timestamp — or the revision column you already emit elsewhere — to io_distributed_jobposting_*. If Fieldglass genuinely does not expose one for postings, a written “not available” is a complete answer and we will model around it.
Why we need it, in one sentence
A Data Vault satellite records when the source asserted a fact, and every version needs a distinct value for that or the history cannot be read back as of a date. We call it applied_dts, and it is deliberately NOT the time we loaded the row — a delivery clock puts every change in one batch at the same instant.
We measured all four candidates before asking 5 Sep, 270,286 valid-key rows over 7,230 postings
ColumnWhat the data saysUsable?
job_posting_create_date 1.0 distinct values per posting — constant, as you would expect from a creation dateNo
uploaded 1.0 distinct per posting, constant for all 7,230 No
job_posting_distribution_date 42.4% nullNo
timestamp The only column that moves at all — but of the 1,127 postings whose content actually changes, it is frozen for 562 of them (49.9%)No

That last row is the one that decides it. Half of all real changes would produce two versions of a posting stamped with the same instant, which is not a history anyone can query as of a date.
Why we think this is a feed gap rather than a Fieldglass limitation
You already carry revision on 62 io_worker tables in fieldglass_raw, and revision_num on others. So the concept exists in the extract; the job-posting tables simply do not include it. That is why this is a short ask rather than a design discussion — and why “not available for postings” is a perfectly plausible answer we would accept.
What it costs to wait — less than you might think
The Fieldglass HUB is already live. As of 4 September hub_job_request holds 7,230 Fieldglass job requests across 30 tenants, loaded through a union view over your per-tenant tables. What waits on this is only the DESCRIPTIVE satellite — title, status, location, positions.

And it waits alongside BRZ-14 anyway: while backfill types are inconsistent we exclude those tables, so Fieldglass HISTORY is not in the vault either. One answer to each and both arrive in the same reload rather than two.
What we will do if the answer is no
Bind timestamp and suppress the type-2 view for this satellite only — keeping insert-only history and openly not offering an as-of-date answer, rather than offering one that is wrong for half the postings. We would rather do that knowingly than discover it later.
Done when
Either a column that changes when a posting changes, or a written confirmation that Fieldglass does not expose one.

BRZ-18

What do Great Plains' account segments mean?

Added 7 Sep
Ask
A table carrying, per segment number and value, its description — GP's segment master. We hold gl00100, which is the account index: it gives the segment values of every combination and no names for them.
Why
A GP account is five segments — 30-60-5600-606502-00 — and Workday wants one ledger account plus worktags. Mapping the other segments onto Workday's cost centres means knowing what they are. We can see GP uses segment-3 value 6120; we cannot see what GP calls it.

BRZ-13

One view per Fieldglass entity, unioning the per-tenant tables

Added 4 Sep
Ask Reduced 4 Sep — we built it
This no longer asks you to build anything. It asked for one view per Fieldglass entity unioning the per-tenant tables. We have built it ourselves and it works, so what remains is the four answers under “what needs deciding” — none of which is a build.
What we built, so you can see what we assumed
metadata/source_unions.yml declares what to union and checks/apply_source_unions.py rebuilds the view from information_schema on every run — so a newly onboarded client is picked up automatically rather than silently missing, and the tenant list each run used is recorded so the change is visible afterwards. It reads your tables and creates nothing in your catalog.

We could do this because a union view over Delta tables is a valid streaming source — measured on serverless: a streaming read of a two-tenant union view resolved to one Delta source per underlying table and ran to completion. That was the open technical question, and it is why this stopped being a dependency on you.
Evidence measured 4 Sep, 01_usnc_bronze_dev
BRZ-2 already recorded the per-client shape on 26 August — “the VMS feeds are already one table per client”. That is not a new finding and this item does not claim it. What is new is the breakdown below, the type problem (now BRZ-14) and the fact that a union view can be streamed from at all.

Corrected: an earlier version of this item said “58 tenant tables”. 58 is the number of TABLES for one family; the tenants number 30. The two must not be conflated, because the difference is entirely the _backfill twins and those are the ones BRZ-14 is about. Per family, live / backfill:

io_distributed_jobposting 30/28 · io_jobposting 34/28 · io_jobseeker 30/28 · io_timesheet 34/28 · io_worker 34/28, plus five co_* families of 1–2 each. 168 live tables and 145 backfill across both Fieldglass schemas. The non-raw fieldglass schema (157 objects) has the same per-tenant shape, so no union exists anywhere today, in raw or conformed form.

The keys are uniform and that is the good news. buyer and job_posting_id are present in all 58 tables — live and backfill alike — so a union can be keyed reliably today whichever way the precedence question is answered. buyer carries a real tenant value (Air Liquide in io_distributed_jobposting_air_liquide).

The payload is not uniform. Column counts run 48 to 52 across four groups (again over all 58, live and backfill): 33 columns appear in every one and 53 in only some. Restricted to the 30 LIVE tables the picture is better than that number suggests — measured, no column carries two types there, which is what lets our union need no casts. Fifteen more carry two different types, which turned out to have a single cause and is now BRZ-14 — it is a data-loss problem in your layer rather than a union problem in ours, so it is stated separately and does not block this item.

Also measured: io_distributed_jobposting_air_liquide holds 77 distinct job_posting_id in 3,779 rows — about 49× re-delivery, which makes BRZ-3's de-duplication question live for this feed too.
What needs deciding — four answers, no build
  1. The _backfill twins, and this is the one that costs us most. BRZ-4 already asks for a precedence rule in the journal domain; the same rule is needed here and one answer covers both. Until it is answered our union EXCLUDES backfill, because every inconsistently-typed column in the estate is in a backfill table (BRZ-14) — which means Fieldglass history is not in the vault. Excluding it is what lets the union need no casts at all: the 30 live tables are type-uniform, measured.
  2. Is io_distributed_jobposting the right family for a job request? We chose it over io_jobposting because it carries 39 columns the other lacks — the posting, requisition and assignment distribution columns, and the max requested/template bill rates — which exist because a posting was distributed TO A SUPPLIER, which is what we are. The two share 43 columns. If the intent is every buyer posting regardless of distribution, we have the wrong one, and the fix on our side is one line. This is a question about your feeds' meaning, not their shape.
  3. fieldglass_client_owned_raw (the co_* tables, client-owned Fieldglass instances). Same view, a separate view, or out of scope? They are Fieldglass postings for HFIG clients either way, so we would rather ask than assume.
  4. Custom fields. We can find no custom-field table in any Fieldglass schema. Our model declares a source for them. Do they exist anywhere, or are the per-tenant extra columns above what “custom fields” means here?
What we have already done 4 Sep
hub_job_request is now key_style: tenant_scoped with the tenant as its first key position, so two clients' identical posting references cannot collide into one hub row. That re-keys 45,517 hub rows, 46,889 satellite rows and 45,517 staging-log rows — a truncate and reload on our side, scheduled with the change rather than asked of you.

We also corrected two things of our own that this investigation exposed: the bindings were named FIELDGLASS_EU, and there is no EU instance — the instances are US, UK and APAC — and the key columns were recorded as buyer_code/posting_id when they are buyer and job_posting_id. Both were guesses made before anyone looked at your tables. UK and APAC are deliberately not declared until their lakes' Fieldglass bronze is confirmed.
Done when
Four answers. Nothing to build.

Data quality
Ask

Why
