# Databricks Industry Data Models — what is worth taking

**Read 3 September 2026.** Two Databricks papers plus the `payments_fintech` model in the
Industry Solutions repo, assessed for use on the HFIG Data Vault accelerator — specifically
for diagramming and ontologies.

Sources:

- `Jumpstart your Data Modeling with Databricks Industry Data Models` (blog, 10 June 2026)
- `Lakehouse Business Data Models for Financial Services & Insurance` (architecture centre)
- `databricks-industry-solutions/lakehouse-industry-data-models`, `data-models/payments_fintech/v1/mvm`

## What they actually are

Forty pre-built **Silver-layer analytical base models**, one per industry, generated by a
rules-driven agent against 200+ structural rules and deployed straight into Unity Catalog. Each
ships in two scopes — MVM (30–50% of the table count) and ECM (full enterprise breadth) — from
one `model.json`, with three cataloguing styles (one catalog, catalog per division, catalog per
domain).

Financial Services has four: Banking, Payments & Fintech, Health Insurance, Life Insurance.
Payments & Fintech MVM is 15 domains / 223 tables / 7,890 attributes / 1,624 FKs / 71 metric
views; its ECM is 18 / 546 / 16,916 / 2,188 / 95.

Every model follows one hierarchy — Organization → Division → Domain → Subdomain → Product →
Attribute — with a rule (G06-R001) forcing Operations + Business to be ≥80% of domains and
Corporate ≤20%.

## The mismatch that decides how we use them

**These models *are* the Silver layer.** The blog is explicit: "Silver holds the conformed
analytical base model that every analyst, BI tool, and data scientist reads from… These base
data models are the Silver layer."

**Our Silver is a Data Vault, and we decided the opposite on 26 August:** the raw vault is not
consumer-readable and the business vault is reached only through Gold. A Databricks industry
model is a normalised, analyst-facing business model. A Data Vault is a historised audit model.
Both call themselves Silver; they are different paradigms with incompatible purposes.

So these are **not a drop-in, not a replacement, and not a competitor** for our silver layer.
Attempting to reconcile them would mean abandoning either the vault or the policy.

**But they are a strong blueprint for the layer we have not built.** Gold does not exist —
`03_usnc_gold_edm_dev` has never been created — and Gold is now a business blocker: every
consumer request has no answer until it exists, which we have just told the platform team in
writing. A normalised, analyst-readable, FK-validated, metric-view-bearing model is exactly
what Gold should be. **Banking** is the closer fit for our finance domain (account, ledger,
finance) than Payments & Fintech.

## On the financial content specifically: mostly off-domain

Worth saying plainly, since the financial models were the reason for looking. HFIG is staffing
and recruitment — job requests, timesheets, workers, payroll, GL journals, AP/AR. Payments &
Fintech is cards, acquirers, chargebacks, settlement, MIDs, interchange. That is not our
business. Health and Life Insurance are irrelevant. Banking's ledger and account domains are
the only substantially reusable content, and even there our GL is a staffing company's GL.

**The value here is the artefact pattern, not the model content.** Which is fine — that is
also the part that transfers.

## Diagramming: take it, and do it better than the reference

`diagram/payments_fintech_dbml_v1_mvm.txt` is a DBML schema for dbdiagram.io. Inspected, the
reference implementation is weaker than it first appears:

```dbml
Table transaction.payment_txn {
  payment_txn_id varchar [pk, note: 'Surrogate primary key ...']
  acquirer_id varchar [note: 'Foreign key linking to settlement.acquirer. ...']
  ...
}
```

**There are no `Ref:` blocks.** Foreign keys exist only as prose inside `note` attributes, so
dbdiagram draws tables with no relationship edges — the one thing a diagram is for. Schema
qualification and `[pk]` are used; NOT NULL, indexes and table groups are not.

**We have no vault diagram at all today, and everything needed to emit a good one already
exists:**

| what DBML needs | where we already have it |
|---|---|
| tables | `spec.load_model()` — 21 entities, 25 tables |
| columns + SQL types | `data_contracts/*.yaml` (generated; carries `type: TIMESTAMP` etc.) |
| primary keys | `naming.hk()` — the hash key per entity |
| foreign keys | `entity.parents` — the real edges, e.g. `journal_line → accounting_journal, organisation, ledger_account, pay_period` |
| classification | `sensitivity`, and `masks` per column |

So a `tools/emit_dbml_diagram.py` fits the pattern this repo already uses four times
(`emit_data_contract`, `emit_source_contract`, `emit_control_contract`,
`emit_quality_dashboard`): generate, commit, and let `verify_repo` assert regeneration is
byte-identical so the diff is the review.

**And it should emit real `Ref:` lines**, which the reference does not. A Data Vault's edges are
its whole point — every link and satellite hangs off a hub — so a vault diagram without
relationship edges would be worth almost nothing.

## Ontologies: a better fit for a Data Vault than for their own models

`ontology/payments_fintech_rdf_v1_mvm.ttl` is RDF/Turtle for "semantic-tooling integration and
AI-agent grounding". Inspected, it is thin:

```turtle
@prefix ind: <http://datamodel.lakehouse.org/business/payments_fintech#>
ind:Business rdf:type rdfs:Class ;
    rdfs:label 'Business' ;
    rdfs:comment 'Root class for all business entities' .
ind:PaymentsFintech rdf:type rdfs:Class ;
    rdfs:subClassOf ind:Business ; ...
```

Tables become `rdfs:Class`, nested by `rdfs:subClassOf`, with `label` and `comment`. There is
**no `rdfs:domain`/`rdfs:range`, no `owl:ObjectProperty`, no explicit PK/FK, and no
classification tags** — relationships survive only as English inside `rdfs:comment`. As an
ontology it is a labelled class hierarchy; the semantics are in prose.

**A Data Vault maps onto RDF considerably better than a normalised schema does**, because the
vault already separates the three things an ontology wants separated:

| Data Vault | RDF/OWL |
|---|---|
| **hub** — a conformed business concept with a business key | `owl:Class` — the entity itself |
| **link / NHL** — a relationship between concepts | `owl:ObjectProperty` with real `rdfs:domain` and `rdfs:range`, from `entity.parents` |
| **satellite** — descriptive attributes over time | `owl:DatatypeProperty`, typed from the data contract |
| `sensitivity` / `masks` | annotation properties — the classification the reference omits |

That is not an adaptation of their approach; it is a stronger use of the same target format,
available to us precisely because our silver is a vault. If we ever want AI-agent grounding over
the model — and `meta_vault_model` already publishes the model to the lake for exactly that kind
of consumption — this is the honest way to express it.

## What to skip

- **The MVM/ECM scoping.** We have one model for one business, driven by `active_sources` per
  target. A second scope axis would add ceremony with nothing to decide.
- **The six-level hierarchy and the 80/20 division rule.** We have `domain:` already
  (`finance`, and others). Division and Subdomain layers would be vocabulary for its own sake at
  21 entities.
- **The "Modeling Agent" / natural-language evolution.** Our model is declarative YAML behind
  917 verification checks and mutation-proven gates. Natural-language directives are a weaker
  control than a reviewed diff, not a stronger one.
- **The model content.** See above — off-domain.

## Recommendation, in value order

1. ~~**Emit DBML from `metadata/entities/`.**~~ **DONE 3 Sep** —
   `tools/emit_dbml_diagram.py` → `diagram/hfig_data_vault.dbml`. 25 tables, 369 columns,
   **31 real `Ref:` edges**. One file, not one per target: measured, all 369 columns carry
   byte-identical types across targets, so the model is target-invariant and a diagram of the
   model should show the model. Every derivation comes from `accelerator.contract` — the module
   whose job is exactly column type, classification, grain and foreign keys — so the diagram
   and the published data contracts cannot disagree.
2. ~~**Emit an RDF/OWL ontology from the same model.**~~ **DONE 3 Sep** —
   `tools/emit_ontology.py` → `onto/hfig_data_vault.ttl`. 12 classes, 18 object properties,
   157 datatype properties, **1,282 triples, validated with `rapper`**. Links are reified as
   classes with one object property per parent, because `owl:ObjectProperty` is binary and
   `journal_line` has four parents. Satellite payload becomes datatype properties on the
   concept described, annotated `dv:sourceTable` so the historisation is not lost. Undeclared
   types get **no** `rdfs:range` rather than a guessed `xsd:string`.
3. **Read Banking's ECM as a Gold blueprint** when Gold is stood up — domain list, metric views,
   FK discipline. Not as silver, and not as content to copy.

## One caveat on the whole exercise

Their 200+ rules and static analysis are the same discipline this repo already applies, and the
papers give no evidence the rules were mutation-proven — which is the thing this project has
learned to insist on, having found more than a dozen checks that could not fail. Treat "200+
enforceable rules" as a claim of the same shape as our own check counts: meaningful only if the
checks can be shown to fail when the rule is broken.
