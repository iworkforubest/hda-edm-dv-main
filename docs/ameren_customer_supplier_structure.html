MSP001 Ameren · Party structure · Data & AI

The identifiers already exist. Nobody is asking for them.

An analysis of the customer and supplier structures in MSP001_Ameren.xlsx, the future-state invoicing design for one of 54 MSP clients. The modelling question is small and the finding underneath it is not: Fieldglass already carries a code for every party in this flow, and the design drops all of them — twice. One worksheet then asks people to key in by hand what the feed supplies for free.

Analysed 23 September 2026 Source: MSP001_Ameren.xlsx, 8 sheets Sample: 225 invoices / 555 lines From data_platform_operations

The shape of the deal, because the model follows from it

This is an MSP principal arrangement, and that makes it a three-party flow with a fourth party on every line. Guidant Global, Inc. invoices Ameren as principal, and separately pays 23 suppliers who employ the 161 workers appearing in this extract.

One Fieldglass invoice line therefore creates two financial obligations with two different counterparties — a receivable from Ameren and a payable to a supplier — and the source states both, along with the margin between them:

Invoice Amount 122.52 <- what Ameren is billed Invoice Line Item Amount (Supplier) 120.00 <- what the supplier is paid MSP Line Amount 2.52 <- our margin, stated per line Gross Invoice Amount 2450.40 Gross Supplier Invoice Amount 2400.00

That is not a derived figure we have to reconstruct — it is a source field. Any model that carries only one of the two amounts throws away the margin and forces someone to recompute it later from two systems.

The finding — identifiers exist, and are discarded twice

Once between source and master data, once between source and output. Neither loss is recorded as a decision.

This is where the first version of this analysis was wrong, and the lake corrected it. The second half is false. Measured against the lake:

Supplier Code is listed in the workbook as a field of the Invoice Buyer Without Status Change Download — an extract this estate does not receive. Nothing we are sent carries it. So the identifier is not waiting to be extracted; it has to be asked for, and that is a different request to a different team.

The master-data sheet is manual and is out of scope — confirmed by Adrian. It is described here only because it was the route by which the missing identifier was noticed.
Why this matters more than the keystrokes saved
A hand-populated identifier is a second source of truth that starts drifting immediately: it is captured once, at a moment, by someone reading a name. The feed carries the code on every line of every invoice, for ever. Only the Workday IDs genuinely need confirming — those exist nowhere in this flow. The VMS IDs need extracting, not confirming, and that is a different task assigned to a different person.
What the lake does carry, and why it is worse
The supplier arrives as a name, in two columns that disagree. From io_timesheet_ameren, 182,914 rows:

Zempleo/Zempleo, Inc. · Envision, LLC/Envision · Iconma, LLC/ICONMA LLC. parent_supplier is not a hierarchy — it is a second spelling of the same company on all but ten rows of 182,914. The lake holds 29 suppliers against the sheet's 23, and one is Lorien, an HFIG brand — an intercompany relationship nobody has mentioned.
The lesson, since it keeps recurring
Every finding in the first version of this section came from reading the workbook, and the central one was wrong. The finding that came from querying the lake was right. That is the fourth time on this programme; it is why the design spec states measurements before decisions.
AME-B

The invoice output identifies no supplier and no worker

Design consequence
What the 13 GIE fields carry
Invoice Number, Invoice Date, Invoice Amount, Description, Line Description, Line Number, Line Type, Amount, Accounting Date, Project Number, Task Number, Expenditure Type, Expenditure Organization. No supplier field of any kind. The worker appears only inside two concatenated text fields, as Last, First:
Description AEE1IN00123410|Kaver, Joseph|2026/07/26|AEE1TS00126533 Line Description Kaver, Joseph|2026/07/26|AEE1TS00126533
This is correct, and it has a consequence
Ameren is billed by Guidant as principal, so the customer invoice should not name the supplier. But it means the Gold output cannot be decomposed back to supplier or worker. The line that ties an invoice line to the party we owe, and to the person who did the work, exists only in Bronze and Silver — and Worker ID is dropped even though the source provides it.

The vault is therefore the only place that relationship survives, which makes it a modelling requirement rather than a nice-to-have. Reconstructing it later from Last, First text is the same class of mistake as identifying a company by its name, and 161 workers is easily enough for two to share one.

Business keys — and the one question that must be answered first

Three of the four keys are settled by the data. The fourth is a business question with a silent failure behind it.

Fieldglass namespaces almost everything by buyer, which does most of the work for us

Buyer Code AEE1 Invoice ID AEE1IN00123410 <- AEE1 prefix Invoice Line Item Ref AEE1TS00126533 <- AEE1 prefix Worker ID AEE1WK00000319 <- AEE1 prefix Supplier Code B3G4 <- NO buyer prefix

Invoice, line and worker identifiers are already globally unique across all 54 clients, because the buyer code is embedded in them. They need no tenant-scoped rekey. Supplier Code is the exception, and it is the one that matters.

AME-C

Is a Supplier Code unique across all 54 MSP clients, or only within one?

Blocks the supplier hub
The question
B3G4 identifies Business Integra for Ameren. Does B3G4 mean Business Integra for every other MSP client too, or is it a code allocated within Ameren’s Fieldglass tenant that another client could reuse for a different supplier?
Why it cannot be deferred
It decides the hub's business key, and the two answers are not refactors of each other:
  • Global → key on supplier_code alone. One supplier row serves all 54 clients, and cross-client supplier spend is answerable.
  • Per buyer → key on (buyer_code, supplier_code), tenant-scoped. Cross-client spend then needs a deliberate matching exercise, because the same firm holds different codes per client.
The failure mode if we guess wrong, and it is the dangerous kind
If codes are per-buyer and we key on the code alone, two different suppliers collapse into one hub row. Nothing fails. No constraint is violated, no gate goes red, every load succeeds. The only symptom is that payables and supplier spend are wrong one level up — discovered, if at all, by someone querying a total that looks implausible.

This is precisely the defect we retired on cost centres (WDJ-10), where the business confirmed a single global meaning and made the code safe to key on. The same confirmation is needed here, and the same rule applies: a dimension may be keyed on its code alone only once someone has confirmed the code means one thing across the whole estate.
How to answer it cheaply
Pull Supplier Code and Supplier from the Fieldglass extracts of two or three other MSP clients and check for a code appearing against two different supplier names, or one supplier name holding two codes. That is a measurement, not a meeting — and on this evidence it is the first thing to do.
AME-D

Supplier name is not a candidate key, and these 23 names show why

Evidence
What is in the list
Adaptive Solutions Group (WoodRibble & Twyman) <- parenthetical qualifier Strategic Staffing Solutions, S3 <- trading alias appended Iconma, LLC / CSI IT, LLC / SBS Creatix, LLC <- legal form in the name Business Integra, Inc. / Zillion Technologies, Inc / Colaberry Inc <- "Inc." vs "Inc" vs "Inc,"
Why it fails as a key
Legal form changes without the company changing. Trading aliases get appended and removed. Punctuation of Inc. is inconsistent within this single list of 23. A name is a description of a party, not its identity — the same argument that settled LEG-1 for legal entities, arriving here from a different direction.

Since the name is currently the only populated identifier for all 23 suppliers, the master sheet as it stands is keyed on the one field that cannot be a key.
AME-E

Supplier-to-client is a relationship, not an attribute

Modelling
What the sheet shows
All 23 suppliers carry Client ID VMS = AEE1, as a column on the supplier record.
Why that shape will not hold
Across 54 MSP clients, a supplier serves more than one — a staffing firm of this size almost certainly appears on several. Holding the client on the supplier record makes the supplier per client, which either duplicates the supplier 54 times or silently overwrites.

It is a many-to-many relationship that is effective-dated: suppliers are onboarded and offboarded per client, and the dates matter for payables. That is a link with its own satellite, not a column.

This is the same distinction the business drew for legal entities in LEG-3 and LEG-5 — ownership and contractual relationships held separately from the party record, effective-dated — and it arrives at the same answer independently.

What the sample data actually proves

The stated controls were tested against the 555 lines rather than taken on trust. They hold.

Three controls pass; one is untested by this sample

Measured
Tested and clean
AME008 sum(line Amount) == Invoice Amount 0 failures / 225 invoices AME003 gross repeated on every line 0 inconsistencies AME006 line numbers a complete 1..n sequence 0 gaps
225 invoices, 555 lines, 2.47 lines per invoice. The reconciliation that the whole Gold release gate depends on holds exactly on this sample.
The rule this sample cannot test
There is exactly one TAX line in 555. AME008's tax half — aggregate tax onto a final TAX line, with all lines still summing to gross — is therefore effectively unexercised. A sample where 554 of 555 lines are ITEM proves the simple path and says almost nothing about the path with tax on it. Worth a deliberate test case before go-live rather than discovering it on a client with real sales tax.
A grain fact worth knowing
81 of 225 invoices span more than one Project Number, and there are 279 distinct projects across 225 invoices. An invoice is not a project-level document, so anything assuming one project per invoice is wrong more than a third of the time.

What we would do first

One measurement, then one decision. Pull Supplier Code and Supplier from two or three other MSP clients' Fieldglass extracts and look for a code carrying two names, or a name carrying two codes. That settles AME-C, which is the only thing genuinely blocking the supplier hub, and it needs nobody's diary.

And stop the hand-keying before it starts. The VMS supplier IDs are in the feed. Only the Workday IDs need a human, and only because they exist nowhere in this flow yet.
