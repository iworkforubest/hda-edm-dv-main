The rule we built on

Every line carries its own client amount — we don't have to derive it from the totals.
Invoice_Amount = Invoice_Line_Item_Amount_Supplier + MSP_Line_Amount holds on 1,172 of 1,172 lines

This matters more than it looks. It means the invoiced value is a property of each individual line, not something we reconstruct by adding a margin at the invoice level. Every line can be shown to Ameren with its own cost and its own fee, and the document adds up by construction rather than by adjustment.

But we have not turned that into a rule, and we would like you to agree

We built the identity, not the pattern

It would be easy to encode "MSP only ever appears on timesheet lines" as a validation rule, and everything we measured would support it. We have deliberately not done that, because you told us the variety is real, and one client's single weekly extract is not a rule.

What the warehouse enforces is the arithmetic — that each line's invoiced value equals its cost plus its fee, and that the lines sum to the invoice total. If an MSP fee turns up on an expense line next month, nothing breaks and nothing is rejected; the invoice simply carries it. Had we encoded the pattern, that invoice would have failed validation and landed in an exception queue for no good reason. Does that match how you expect this to behave?

To be clear on the invoice date: we generate it, we just need the rule

The invoice date and line numbers are computed in Databricks and issued once, then frozen — so the date on Ameren's copy and the date in our warehouse can never drift apart, even if the invoice is regenerated. GIE renders the document; it does not decide the date.

So this is not a system question, it is a one-line business answer: what date should the invoice carry? The sample suggests it behaved as the release date — Invoice Date had a single value across all 225 invoices while Accounting Date had 14 — but we would rather be told the rule than infer it from one file, because the code deliberately refuses to default it.
