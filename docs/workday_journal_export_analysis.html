WDJ-2

The hash cannot be the Workday identifier — this one is a correction, not a choice

Design
What the sheet says
AccountingJournalID = “Hashkey from Databricks”. That is accounting_journal_hk, a SHA-256 BINARY(32).
Why it cannot work
A hash key is derived, not issued. Its value is a function of two things that are both allowed to change, and no amount of engineering on our side makes either of them permanent:
  • The rulebook. Algorithm, binary-vs-hex, casing and separator are versioned in our code precisely because they may change. Exporting the value inverts the reason it is versioned: an internal, revisable constant becomes an external, immutable one.
  • The business keys. UKG supplies no fiscal year, so we hash the literal NOT_APPLICABLE. That is a placeholder waiting for a value, not a fact — and the day UKG supplies one, every UKG journal re-keys.
    business_keys: [reference_type, organisation_reference_id, fiscal_year, reference_id]
What is wanted
An external identifier must be issued once and stored. Every key in this vault is deliberately the opposite — recomputable, so that two lakes deriving independently agree without coordinating. Recomputability is the whole design, and it is exactly what an external permanent identifier must not have. There is no Databricks-side mechanism that reconciles the two.
A one-way door
The constraint does not begin when we notice it. It begins the moment the first file lands, and it applies retroactively to every journal already sent.
The fix
Workday mints the ID. Three parts, and only the third is work:
  • Workday generates AccountingJournalID — it is their key, in their system, under their control.
  • We send JournalExternalReferenceID carrying the source system’s own identifier as that system spells it. The sheet already describes this field as “use when source system provides a value”, which is precisely what it is for. It must be a readable composite, not a bare key: GP’s jrnentry is unique within a company and year, UKG’s batchid within a company.
  • We capture Workday’s ID back so reconciliation does not depend on our key staying stable either. This is the one part that is new work — and it may be much less than it sounds: the same Reference Service in WDJ-5 returns the instances and ids for a reference ID type, so if journals are retrievable by their external reference id, the return path is a call rather than a build. Worth asking before scoping it. It is also the same return path WDJ-1 is about.
What it removes
It removes the rulebook dependency entirely and the hex-encoding question with it. It does not remove the business-key dependency: whatever we send as an external reference is externally frozen, readable or not. Capturing Workday’s ID back is what removes that last one, which is why it is part of the recommendation rather than a refinement of it.
Sizing it
Now a cheap experiment. We looked. External_Reference_Id is a reference ID type in v46.2, and retrieving it from headfirst3 returns zero rows — consistent with nothing having been loaded with an external reference yet, rather than with the mechanism not existing. Accounting_Journal_ID returns 21 journals whose ids are Workday’s own (ACCOUNTING_JOURNAL-6-1), which is what we would expect it to mint for us.

So load one journal with a JournalExternalReferenceID and retrieve External_Reference_Id again. If it appears, the return path is a call we already have and this recommendation costs nothing beyond it. If it does not, it is a bespoke build. One test journal answers it.
Done when
The Workday team confirms Workday mints AccountingJournalID, and we agree the composite format for JournalExternalReferenceID per source system.

WDJ-10

Is a cost centre global, or does the same code mean something different per region?

Business question
Why we ask
Workday is one global tenant. Our Data Vault is four regional lakes — Western Europe, UK South, US North Central, Australia East. So a piece of global reference data has to mean the same thing in all four, or be scoped so it cannot be confused.
What your tenant already answers
The structure looks global, and clearly so:
  • 64 live cost centres, one list, no regional marker on any of them. The only name containing “Region” is C4200 Regional Marketing, which is a function called that, not a region.
  • Geography is a separate dimension. Region_Reference_ID carries 99 entries — REGION-Americas, REGION-APAC, REGION-Europe, REGION-UK_&_Ireland — and the custom organisations carry NA, APAC, UK&I, DACH, Benelux, Iberia, Nordics, CEE and the Baltics.
So the question is narrower
Not “is the list global” — it evidently is. Does a cost centre carry the same meaning everywhere? Is C6130 Engineering one cost centre that four regions all charge to, or four regional engineering functions sharing a code?
Why it matters to us, precisely
Our hub keys are hashed from business keys. If the meaning is global, the key is the code and one cost centre is one row in all four lakes — which is what makes our cross-region conformance check compare like with like. If the meaning is regional and we key on the code alone, two different cost centres collapse into one row, silently. Nothing would fail; the numbers would simply be wrong at every level above.
We have made this mistake’s twin before
It is the same shape as the buyer column in our VMS feeds, which carried three different things under one name and read as one. That took a fortnight to model out. Getting this wrong is cheap to do and expensive to find, which is why it is a question rather than an assumption.
Ask
One sentence from finance: a cost centre means the same thing group-wide, or it does not. If it does not, tell us what scopes it — company, region, or something else — and we will key on the pair.
Done when
Confirmation either way. Both answers are workable; only the silence is not.
ANSWERED 8 Sep — CLOSED. Cost centres are global, and this closes a silent defect
Amy Keser, with Alex in group finance, and she states high confidence because she worked on the design: a cost centre is globally governed reference data with one consistent business meaning. It represents a business function, ownership structure or cost accountability and must not mean different things by region. Regional, legal-entity and management reporting are served by separate dimensions — Legal Entity, Region, Company, Business Unit, Worktags — never by reusing a cost centre code with a second meaning. Exceptions go through separate organisational structures.

This closes the question at exactly the condition we wrote down. The rule recorded in the source design was: a global dimension may be keyed on its code alone only once someone has confirmed the code means one thing group-wide. That confirmation now exists, with a name and a reason attached, so cost centre keys on the code.

What it retires is a defect that would never have announced itself. Had cost centres been regional and we keyed on the code alone, two of them would have collapsed into one hub row, every gate would have stayed green, and the only symptom would have been totals that were quietly wrong one level up. That is the buyer defect with a different column name, and it is now off the table rather than merely unobserved.

Raw vaultalready built hub_accounting_journal, hub_organisation, hub_ledger_account, hub_pay_period, nhl_journal_line, nhl_general_journal_line (+ closed year), sat_accounting_journal_header, msat_journal_line_worktag, msat_journal_line_external_code One header, many lines, many worktags per line — hub+satellite, link, multi-active satellite. The same nesting Workday’s XSD describes.
Business vaultcomputed satellites Line ordering for UKG (WDJ-4); the reference + userdefined1 memo rule Both are derived and reusable. A rule that lives in export SQL is a rule the next consumer re-invents differently.
Reference dataplatform-owned, read by join The Workday reference-type enumeration; the company and ledger-account crosswalks (WDJ-5) Supplied, not derived. A crosswalk somebody maintains is governed configuration — the accelerator consumes it and never creates it.
Goldthe export itself Header, lines and worktags projected into the load format; constants applied; filtered to what the use case needs This is the only genuinely use-case-specific piece, and it is a projection. Nothing structural.

The part that needs no work

msat_journal_line_worktag was modelled from the Workday XSD before this worksheet existed: one row per line and worktag type, with the XSD’s own constraint — “only one worktag for each type is allowed for each document line” — expressed as the satellite’s key and enforced as a data-quality expectation rather than assumed. WorktagsReferenceID is the hardest field on the Line section and it is the one that needs the least thought.

What we are not asking for

The 25 fields answered No need nothing from anyone — they are Workday features HFIG does not use (ledger amounts, quantities, reversals, book codes, control totals, spend-report exclusion). The 6 marked TBD are noted and not blocking; the two that would change the model if they turned into Yes are IncludeTaxLines, which pulls in all of WDJ-6, and LineCompanyReferenceID, which would mean a line can belong to a different company from its header.
