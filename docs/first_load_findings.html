What only a live run could find

Before this load the repository held 335 unit checks and 534 repository checks, all passing, against a vault holding nothing. Those checks are genuinely valuable — they caught identity collisions, tautological guards and silent orphans. They are also structurally blind to whether the platform behaves as the design assumed.

One constraint explains three separate failures

A streaming table cannot read its own contents. Change detection needs to compare incoming rows against what is already stored; the year-end close needs to recognise a row it has already seen; a hub needs one row per business key however many sources supply it. All three are the same operation, and the platform refuses it.

Two were solved — change detection by delegating to the source, the year-end close by splitting one entity into two. The third is still open, and the entity split could not fix it because both entities share a hub.

Three documented platform assumptions were refuted by contact with the runtime, and two undocumented behaviours surfaced: a task fails on a clean exit as readily as a failing one, and a pipeline library cannot locate itself. Neither is discoverable offline.

The gates themselves were not working

The append-only check — the sharpest assertion in the repository — filtered the catalogue for managed tables, while every vault object is a streaming table. It could never have seen a single table, in any region, ever. It failed loudly only because someone had written an explicit "no tables found" guard; without it, the check would have exited successfully having asserted nothing.

Separately, no gate could report success at all: a clean exit was treated as a task failure, and the scripts died before running on a path resolution that does not exist in that runtime.

Three decisions

None of these can be settled from the code. Each needs someone with authority over the estate.

1

Mask group mapping

Blocking three gates

The governance SQL grants to hfig_data_engineering, hfig_analysts and hfig_commercials_reader. None exists. The estate uses a different convention entirely — usnc_data_platform_bronze_layer_reader, us_tds_bi_builder, usnc_data_custodian_fieldglass, pii_cleared_us.

This is the third item on the README's own reconcile before first load list, never done. The masks work correctly and deny to everyone, including the gate that verifies them — so the journal integrity check reads every amount as null and refuses to assert. The data is intact behind read-time masking.

The governance step also revokes on the shared bronze catalogue, which this project did not create. A revoke is unconditional and lands; the grant that follows names a group that does not exist and fails. Running it unmapped would leave nobody able to read bronze. It is held at a documented stop.

needsA mapping from the four placeholders to real account-level groups, and a decision on whether this project should alter permissions on a catalogue it does not own.
2

Hub deduplication

Open modelling defect

A hub holds one row per business key regardless of how many sources supply it. Two hubs do not: the journal hub carries 538,186 duplicate keys, the organisation hub 11.

This is not a loading error. 538,186 journals genuinely exist in both the open-year and history tables, and each binding deduplicated correctly within itself. Collapsing across bindings requires reading the hub's own contents, which is the constraint above.

AA deduplication step outside the pipeline. The documented fallback, and the same answer change detection will need. Adds a stage the design did not have.
BDeduplicate at read time through a view over each hub. Cheap, but every consumer must use it, and nothing enforces that.
CRecompute hubs rather than append to them. A hub is conceptually a set of keys, so this is defensible — but it abandons the append-only guarantee the vault is built on.
3

Clustering

Performance regression

Nothing in this model can be a clustering column. Hash keys are binary, which the storage layer refuses to cluster on, and the load timestamp falls outside the statistics window on an 85-column journal. Clustering is switched off entirely.

Hash-key joins are the Data Vault access path, so this is a real regression against the design's intent on a six-million-row table that will grow.

AWiden the statistics window so the load timestamp is indexed. A table property, reversible, touches nothing ratified.
BMake hash keys strings so they can be clustered. This changes a ratified constant and re-keys everything — cheapest now, while one region holds one load, and progressively more expensive after.

What this cost, and what it bought

Forty-three defects were found and recorded across the retarget and this sub-project; fifty-eight decisions were taken and written down with their reasoning and what each costs if wrong. Sixty-five commits. The offline suites grew from 123 and 406 checks to 335 and 534.

The defects worth the effort were not the ones that broke a build. They were the ones that would have passed every check and produced wrong data quietly: a link and its parent hub computing different keys for the same identity; an account index merging eleven companies; journal entry numbers colliding across fiscal years; a guard whose condition could never be true; a mask clause that had never once been valid SQL.

Each was found because something insisted on evidence rather than agreement — and the last of them only because the vault was finally asked to hold real rows.
