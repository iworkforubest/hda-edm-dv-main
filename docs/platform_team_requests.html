PLT-3

A deployment folder outside /Shared

2 · every deploy warns, world-writable
Ask
One folder per workspace, owned by data_platform_operations, with users holding nothing — no entry, direct or inherited:
databricks workspace mkdirs /hfig-platform --profile <workspace>
Why it matters
Bundles deploy the pipeline’s source code to the bundle root, and Lakeflow executes that code under the run-as identity, which is privileged against the raw vault. The measured ACL on the deployed folder gives users CAN_MANAGE, inherited — so any workspace user can rewrite the code the vault runs. That does not defeat the column masks so much as go around them.
What it is blocking now
A finished quality dashboard cannot be released to business users. The publishing mode they would need runs queries as the publisher, for whom masks resolve to cleartext, and any user can repoint one of its queries at the raw vault. We shipped it with that mode disabled and a build check preventing re-enablement, so nothing is exposed — but the feature is finished and withheld.
And it hides every other warning
bundle validate --strict promotes warnings to errors, so this one standing warning fails the command outright and no other warning can ever be seen behind it. We deliberately have not silenced it: making the root a variable suppresses the message without changing the permission.
Why we cannot fix it ourselves
Declaring bundle permissions cannot revoke an inherited grant, and the same block would widen the vault_load ACL — the opposite of what is wanted. Deploying to a personal folder works and ties the estate to one account. Creating a top-level folder is denied to us; it needs workspace admin.
What changes on our side
One line — bundle_root_prefix is already a variable and all eight targets follow it.
Answered 7 Sep, and it is a better answer than our ask
The reply was “deployments through the repository should cover this — bundles are released to the service principal's workspace directly, which normal users don't have access to.” We would rather do that than have a folder created for us: it removes the laptop from the deployment path entirely, which is a better outcome than a restricted folder we still deploy into by hand.

It has not changed anything yet, and cannot until PLT-1. What we deploy today still targets /Shared and still warns, measured 7 September:
$ databricks bundle validate --target usnc_tds Warning: the bundle root path /Workspace/Shared/.bundle/hfig-dv-accelerator/usnc_tds is writable by all workspace users
To take the repository route we need the service principal's name and its workspace path — the same input PLT-1 and PLT-4 are waiting on. bundle_root_prefix is already a variable, so pointing it there is one line.
If the answer is no
Tell us and we record it as an accepted risk for TDS. It must not stand for production, where the run-as identity holds production catalog rights.

The cause was ours, indirectly
Our own write access was implemented by adding the silver catalogs to the full_scopes roll-up groups, which propagate a standard privilege set including SELECT onto every schema in their catalogs. Nothing was misconfigured and nothing came from our governance job — apply_masks.sql is built not to emit a schema grant and says so at the site. What was missing was a carve-out, which did not exist because the catalog was empty when it was wired up. A hand revoke would not have held.
THE ARGUMENT, which is why this is kept
A schema grant is not a bigger table grant; it is a different thing. Every streaming table has a hidden companion that SDP creates to materialise it, named __materialization_*. The column masks are declared on the streaming table. They are not on the companion. A grant naming a table conveys that table and the mask applies; a grant on the schema conveys everything in it, companions included — so the holder reads the unmasked twin of a masked column. Money and PII in cleartext, no mask evaluated, and nothing in the audit distinguishing that read from any other.
Why it keeps mattering
This is what checks/schema_grant_check.py encodes, and a temporary schema-level SELECT has been proposed as a convenient bridge twice since the revoke — once by us. Read this before anyone suggests a third.

One thing consolidating this found in our own configuration

service_principal is declared with default: "". The variable directly beneath it, vault_privileged_group, carries a comment saying there is deliberately no default, because “a wrong-but-plausible default is how a grant lands on the wrong principal quietly; an unset one fails at configuration time, naming the target that is missing it.”

By its neighbour’s own rule, an empty-string default is the weaker of the two choices — it resolves rather than failing, and a production deploy would carry an empty run_as rather than refusing. Ours to fix, not Platform’s, and noted here because PLT-1 is what puts a real value into it.
